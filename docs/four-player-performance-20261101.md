# 4人対戦の処理・描画の軽量化（2026-11-01）

## 維持するもの

シミュレーションは従来どおり毎秒60回。入力取得、先行入力、当たり判定、召喚と弾の移動・寿命・命中履歴、CPU、オンラインの進行を描画回数で間引かない。弾・召喚の上限や威力、復帰性能、タイマーの仕様は変更しない。

## 変更

- `game.js`：高リフレッシュレートの表示でも、対戦の同一フレームを何度も描き直さない。更新ループと `Net.pump` は描画を省く回にも必ず実行する。低い描画頻度では従来の固定時間更新で複数回進める。メニュー・ポーズは引き続き描画し、対戦への切り替えも即座に描く。
- 4人時に汎用の装飾火花が大量に重なった場合は、全体に分布する最大240個を描く。弾・召喚・攻撃本体・命中フラッシュ・技固有のエフェクトは間引かない。火花自体の更新・寿命も従来どおりで、描画の密度だけを抑える。
- `battle-hud.js`：HUDは元の高解像度画像の必要な範囲を直接サンプリングする。毎フレームのクリップと未使用の全身ポーズ取得を省き、追加のラスターバッファを作らない。表示倍率や補間は元画像へそのまま適用され、キャラ選択・勝利画面の画像も変更しない。
- `character-vfx-kit.js`：左右反転・回転が不要な描画では同じ座標へ直接描き、不要なCanvasの保存・復元を省く。左右反転・回転・透明度・元の素材と判定へのフィットは維持する。
- `newcomer-system.js`：そのキャラも残留物体もいない場合だけ空の更新を省く。所有者の形態やキャラが変わっても、残っている弾・召喚は動かし続ける。
- `newcomer-vfx.js`：描画関数の一覧を初期化時に作り、毎フレーム同じ一覧を生成する割り当てを省く。登録順・前景の描画順を維持する。

## 比較の方法と結果

`four-player-performance-test.cjs` は変更前のコミット `2ffbc7d` の関連5ファイルと変更後を別ページで読み、同じ4人（モノ・ラチェット・エトナ・ナホビノ）、入力、乱数条件で比較する。負荷用に96物体を初期配置し、通常の入力でも技を発動する。通常対戦の物体上限を変更するテストではない。

| 表示の呼び出し頻度 | 2秒間の更新（前／後） | 描画回数（前→後） |
| --- | --- | --- |
| 30Hz | 120／120 | 61→61 |
| 60Hz | 120／120 | 121→121 |
| 144Hz | 120／120 | 289→121 |

同じ入力で、位置・速度・ダメージ・硬直・技の進行・予約・ストック・弾と召喚の状態・命中履歴が一致。144Hzでは重複描画を約58%削減した。開始時の1回の描画を含む。

96物体と4人の攻撃を描く1回のCanvas操作は、保存・復元が各172→93回、クリップが6→2回となり、画像の描画数は114回のまま。700個の装飾火花の場面は描画700→240個となり、700個すべての状態・寿命と戦闘状態を保持した。

計測中の1回の描画時間にはばらつきがあり、変更後が長くなる試行もあったため、一律の短縮率として扱わない。公開版の再計測を踏まえ、HUDの中間画像を再利用する方式はさらに簡素な元画像の直接サンプリングに置き換えた。重複描画の削減数、Canvas操作数、追加バッファの有無、戦闘状態と画素の比較を検証根拠とし、特定のFPSを全環境で保証する値にはしない。

- 通常密度で変更前後のCanvas全画素が一致。DPR1.5でも世界・攻撃・召喚とHUDに有意な差のある画素は0。PCの実画面でも確認。
- 24種類のHUD画像を順に描き直しても追加Canvasは0。元画像の再表示、VFXの左右・回転・透明度・Canvas状態の復元を確認。
- 所有者のキャラが変わった弾も移動し、寿命で消えることを確認。
- 4人CPU戦2試合、各1800フレーム。全員の攻撃が命中し、位置・速度・ダメージは有限値を維持。サンズを含む既存方式との混在も確認。
- 入力131項目、HUDの可読性60項目、関連5キャラの前景エフェクト35場面が成功。
- `four-player-performance-online-test.cjs`：4クライアント、実キーボード入力、負荷用48物体。描画頻度を通常・1/2・1/4に変えても240フレームの戦闘状態・実命中・物体状態が一致。

検証画像・生の計測結果はGit管理外の `previews/performance/`。素材の追加やアトラス変更はなく、アート全件の再生成は不要。
